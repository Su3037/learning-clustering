01 / Goals and problem

What this module solves

Start with the problem and what counts as success, then the algorithm. Each goal links to where it is taught.

RecapModule 03 的规则不变：每次合并簇间边权和最大的合法一对，选择键逐字段比较，不回撤。本模块只多问一件事：合并后装得下吗？

Learning goals

  1. 区分四个报告项：实际簇数、是否满足容量、是否达到 K、停止原因。大小、容量与四个报告项 · [概念] 合法与目标是两回事
  2. 按“先筛合法、再选最大”的顺序执行带容量的合并，并能指出被阻止的候选。同一张图，两种容量 · [推演] 被挡住时选谁
  3. 用下界 ⌈总大小 / C⌉ 证明某个 K 不可能，并理解满足下界不等于一定可行。不可能，还是走进了死胡同 · [约束] 至少要几个簇
  4. 解释“总体可行，但贪心卡住”（greedy_trap）与“理论上不可能”的区别。不可能，还是走进了死胡同 · [探索] 卡住还是不可能
  5. 解释“合法但非最优”（suboptimal：贪心 18，最优 11），并说明单元大小不同会改变结果。合法，但不是最优 · [探索] 合法但差多少 · [应用] 面积不同，结局不同
  6. 读懂带容量与诊断的伪代码，在 Python 中补全停止报告与分类。伪代码：合并、报告、诊断 · Python

Problem statement

Input

带权无向图、每个节点的大小 s(v)（面积或单元数）、容量 C、目标簇数 K。

Output

合法的簇、cut、实际簇数、capacityCompliant、targetReached、停止原因；可选的穷举诊断。

Objective

在每簇大小之和 ≤ C 的前提下，用贪心合并减少 cut，并尽量达到 K。

Constraints

硬容量：任何一次合并后簇大小都不能超过 C；K 不能凌驾于容量之上；单个节点已超过 C 时输入本身不合法。

Assumptions

簇大小 = 成员大小之和；先过滤合法候选，再按 (−亲和度, 成员, 成员) 选择；穷举诊断只用于 ≤ 10 个节点的教学图。

Stopping

达到 K；或没有合法的正亲和度对（capacity-blocked / no-positive-affinity）。之后用下界与穷举判断属于哪种结局。

From an example to pseudocode

§ 1规则不变，多问一句：装得下吗

合并规则和 Module 03 完全一样：从单点簇开始，每次合并簇间边权和最大的一对，选择键逐字段比较，不回撤。区别只有一条：

先筛合法，再选最大。 合并后的簇大小超过容量 C 的候选，不论亲和度多大，都不能选。

真实电路里，一个簇往往对应芯片上的一块区域，它能容纳的单元面积有限。这条约束看似简单，却让“贪心合并”出现了三种不同的结局。本章的任务就是把它们分清楚。

§ 2大小、容量与四个报告项

单元大小

size s(v)

一个节点占用的面积或资源。本章的 G01 每个节点大小 1，greedy_trap 的 A、B 大小为 2。

容量

capacity C

每个簇允许的大小上限：簇内所有节点大小之和 ≤ C。

合法

capacity compliant

每个簇都满足容量。

达到目标

target reached

实际簇数 ≤ K。

这四件事互相独立，必须分开报告：

报告项含义容量 2、K = 2 时
count实际簇数3
capacityCompliant每簇大小 ≤ C是
targetReachedcount ≤ K否
stopReason为什么停capacity-blocked
K 不能凌驾于容量之上

如果为了凑够 K 而做一次超容量的合并，结果就不再合法。宁可停在更多的簇上，如实报告。单个节点本身已经超过容量时，输入就不存在任何合法分组，本课程把它报告为输入错误，而不是强行合并。

§ 3同一张图，两种容量

在 G01 上取 K = 2，比较容量 3 与容量 2：

步骤容量 3容量 2
1A–B（5），大小 2，合法A–B（5），大小 2，合法
2AB–C（1+4=5），大小 3 ≤ 3，合法AB–C 大小 3 > 2，被阻止；改选 D–E（5）
3D–E（5）剩下 AB+C = 3、C+DE = 3，全部被阻止
结果ABC | DE，cut 3，达到 KAB | C | DE，cut 8，未达到 K

容量 2 时，被阻止的不是“小”候选，而恰恰是亲和度最大的 AB–C。合法性筛选发生在比较亲和度之前。

§ 4不可能，还是走进了死胡同

容量 2 的 G01 停在 3 簇。这是贪心的错吗？先算一个下界：

总大小 = 5，每簇最多 2，所以至少需要 ⌈5 / 2⌉ = 3 个簇。

任何算法都不可能把 G01 在容量 2 下分成 2 簇。这里贪心没有犯错：目标本身不可行。

下界只能证明“不可能”，不能证明“可能”。原作者 GateUltra 的 greedy_trap 图说明了另一种情况：

  • 节点 A、B 大小 2，C、D 大小 1；边 C–D = 10、A–C = 4、B–D = 4；容量 3，K = 2。
  • 下界：总大小 6，⌈6/3⌉ = 2 ≤ K——下界允许 2 簇。
  • 贪心：先合并亲和度最大的 C–D（10），得到大小 2 的 CD；接着 CD+A、CD+B 的大小都是 4 > 3，A–B 之间没有边。停在 3 簇。
  • 穷举：AC | BD 两簇大小都是 3，合法，cut = C–D = 10。

所以 greedy_trap 是“总体可行，但贪心卡住”：第一步拿走了最大的 10，后面就再也拼不出合法的两簇。贪心不回撤，它没有办法发现这条出路。

一个反直觉的细节

贪心停下时 cut 是 8（A–C 4 + B–D 4），比可行的 2 簇方案（cut 10）还小——因为它多了一个簇。cut 小不代表目标达到了；两件事要分开看。

§ 5合法，但不是最优

第三种结局来自原作者的 suboptimal 图：边 A–B = 10、A–C = 9、B–D = 9、C–D = 1，每个节点大小 1，容量 2，K = 2。

  • 贪心：先合并 A–B（10）；之后 AB 已满，只能合并 C–D（1）。结果 AB | CD，cut = 9 + 9 = 18。
  • 穷举：AC | BD 只切断 A–B（10）与 C–D（1），cut = 11。

两个结果都合法、都达到了 K，但贪心比最优差了 7。原因和 greedy_trap 一样：第一步拿走了眼前最大的 10，却把两条 9 都留在了 cut 里。

单元大小也会改变结局

把 G01 中 A 的大小改成 2、容量 3、K = 2：A–B 合并后大小已是 3，AB+C 变成 4 被阻止，贪心改为合并 D–E，再把 C 放进 DE。结果 AB | CDE，cut 5，而不是原来的 ABC | DE、cut 3。“按节点个数”和“按面积”得到的答案可能不同。

§ 6伪代码：合并、报告、诊断

  1. clusters ← 单点簇；若某个 s(v) > C：报告输入不合法
  2. while |clusters| > K:
  3. cands ← 亲和度 > 0 的簇对
  4. legal ← {(P, Q) ∈ cands : s(P) + s(Q) ≤ C}
  5. if legal 为空: stop ← capacity-blocked 或 no-positive-affinity
  6. 合并 legal 中选择键最小的一对
  7. report: count, capacityCompliant, targetReached, stop
  8. diagnose: 下界 ⌈Σs / C⌉ 与小图穷举

Click any line for its explanation. When you step through the lab, the line being executed lights up.

和 Python 的对应：第 1–6 行 → solve()；第 7 行 → report()；第 8 行 → oracle() 与 classify()。

§ 7应用与局限

在芯片设计中，容量约束对应“每块区域能放多少面积”。容量约束的聚类常作为粗化步骤，把大量单元合成大小受控的簇，再交给划分或布局。

  • 下界只能证明不可能；“可能”需要真正找到一个合法分组——这和装箱问题一样难。
  • 本章的穷举只适合 10 个节点以内；真实规模要靠启发式或数学规划，并且通常没有最优性保证。
  • 贪心不回撤。走进死胡同时，它能做的只是如实报告；改进需要允许回退或交换的方法——这正是 Module 07、08 的主题。

08 / Common mistakes and limits

Where it goes wrong

Each entry gives the wrong result, the cause, a counterexample and the fix; every number in the counterexamples is recomputed by the tests.

把“合法”说成“完成”

Wrong result
容量 2 时得到 AB | C | DE，报告“聚类成功”。
Why
合法只说明每簇没超容量；目标是 K = 2，实际是 3 簇。
Counterexample
同一分组在 K = 3 时既合法又达到目标，在 K = 2 时合法但未达到目标。
Fix
四项分开报告：count、capacityCompliant、targetReached、stopReason。

为了达到 K 而违反容量

Wrong result
把 C 塞进 AB，得到 ABC | DE，大小 3 > 2。
Why
容量是硬约束；K 只是目标，不能凌驾于约束之上。
Counterexample
5 个单位大小、容量 2，至少需要 ⌈5/2⌉ = 3 簇——K = 2 根本不存在合法解。
Fix
先算下界；下界大于 K 时直接说明不可能。

把“贪心卡住”当成“不可能”

Wrong result
greedy_trap 停在 3 簇，就断言“容量 3 下不可能分成 2 簇”。
Why
停下只说明贪心这条路走不通；可能还有别的合法分组。
Counterexample
greedy_trap：贪心先合并 C–D（10），之后 A、B 都放不进；穷举找到 AC | BD（大小 3、3），2 簇、cut 10。
Fix
用穷举（小图）或其他方法验证，再下结论。

以为合法结果就是最优

Wrong result
suboptimal 图上贪心得到 AB | CD、cut 18，就当作答案。
Why
贪心先拿了最大的 A–B（10），把两条 9 都留在了 cut 里。
Counterexample
合法的 AC | BD 只切断 A–B 10 和 C–D 1，cut 11。
Fix
“合法”和“最优”分开说；需要最优时要有对照。

把节点个数当成面积

Wrong result
所有单元大小都按 1 计算，忽略面积差异。
Why
真实单元面积不同；容量按大小之和计算。
Counterexample
G01 中把 A 的大小改成 2、容量 3：结果从 ABC | DE（cut 3）变成 AB | CDE（cut 5）。
Fix
输入里明确每个节点的大小。

Scope and limits

  • 下界 ⌈总大小/C⌉ 只能证明“不可能”，不能证明“可能”：装箱问题本身就难。
  • 穷举 oracle 只适合 ≤ 10 个节点的教学图（集合划分数量增长极快）；真实规模需要启发式或数学规划。
  • 贪心不回撤：一旦走进死胡同，只能报告，不能自己找到出路。
  • 本模块只有一种约束（容量）；真实设计还有时序、引脚数等约束（Module 09 讨论延迟）。
