01 / 目标与问题

这一模块要解决什么

先看问题和成功标准，再看算法。每个目标后面的链接指向讲它的地方。

复习上一模块的要点：评分只排名，并且要固定平票规则。本模块选定一种评分——簇与簇之间的边权和——并用它反复合并。

学习目标

  1. 说出贪心合并的输入（图、K、可选容量）、输出（簇、cut、是否达到 K、停止原因）和两条停止条件。连接与局部选择 · 单点簇、目标簇数 K 与簇间亲和度
  2. 计算两个簇之间的亲和度（跨簇边权之和），包括收缩后平行边的相加。单点簇、目标簇数 K 与簇间亲和度 · [推演] 选出下一对
  3. 按 (−亲和度, 成员, 成员) 逐字段比较选择下一对，解释为什么不能把数组当字符串比较。数值优先与平票规则 · [推演] 第一步合并哪一对 · [纠错] 字符串比较选错了谁
  4. 手算 G01 在 K=2 时的完整轨迹 AB → ABC → DE，cut 18 → 13 → 8 → 3，并在结果上画出剩余的 cut。逐步推演：AB → ABC → DE · [探索] 画出剩余的 cut
  5. 解释容量为 2 时为何停在 3 簇（AB+C 大小 3 > 2），并区分“合法”与“达到 K”。容量预览与停止状态 · [约束] 不能强行凑 K
  6. 说出贪心合并的局限（不回撤、依赖评分），并在 Python 中实现带正确比较器的合并。贪心的局限与工程含义 · 逐行读懂伪代码 · [实现] 多位数与小数 · Python

问题定义

输入

带权无向图（节点大小默认 1）、目标簇数 K、可选容量 C。

输出

实际得到的簇、cut、簇数、是否达到 K、停止原因，以及每一步的合并记录。

目标

通过反复合并“最亲近”的一对簇，让跨簇连线（cut）尽量小。

约束

只合并亲和度 > 0 的簇对；若给了容量，合并后大小不得超过 C；不撤销已做的合并。

假设

亲和度 = 两簇之间所有边权之和；选择键 (−亲和度, 簇 A 成员, 簇 B 成员) 逐字段比较。

停止 / 完成

簇数达到 K；或者没有合法的正亲和度簇对（此时如实报告未达到 K，绝不强行合并）。

§ 1连接与局部选择

Module 02 回答了“谁和谁最亲近”。最自然的下一步是：先把最亲近的两个合在一起，再看下一对。这种“每一步只做眼前最好的选择”的方法叫贪心（greedy），从单点开始一路合并的聚类叫凝聚式聚类（agglomerative clustering）。

它的优点是规则简单、每一步都能手算；它的问题也很明确：合并以后不再拆开，早期的选择会影响后面所有的选择。这一章先把规则讲清楚，下一章（Module 04）再专门讨论它会在哪里出错。

§ 2单点簇、目标簇数 K 与簇间亲和度

簇

cluster

一组被放在一起的节点。开始时每个节点自己是一个“单点簇”。

收缩

contraction

把两个簇合并成一个“超节点”：它们之间的边变成内部边，和外部的平行边权重相加。

目标簇数

target K

希望得到的簇数；簇数降到 K 就停。

簇间亲和度

inter-cluster affinity

两个簇之间所有边权的和。本模块只用这一种亲和度。

簇间亲和度为什么是“边权和”？ 因为把两个簇合并，它们之间所有的边都变成内部边，不再计入 cut。所以：

每次合并，cut 恰好下降这一次的亲和度。

这条性质让每一步的效果都可以直接读出来，也是本课程测试检查的性质之一（200 个随机图上每一步都成立）。

§ 3数值优先与平票规则

每一步要从所有候选里选出“最该合并”的一对。本课程固定选择键：

(−亲和度, 簇 A 的成员, 簇 B 的成员)，逐字段比较，取最小。

第一字段取负号，是为了让亲和度大的排在前面；后两个字段在平票时按成员名字的字典序决定。比如 AB–C 和 D–E 都是 5，比较成员列表 [A, B] 和 [D]：A < D，所以先合并 AB–C。

原网页里的比较器错误（已在本课程修正）

原作网页的 JavaScript 写成了 if (!best || cand < best)，其中 cand 是数组。JavaScript 比较两个数组时会先把它们转成字符串：[-1, "A", "C"] 变成 "-1,A,C"，[-5, "A", "B"] 变成 "-5,A,B"。字符 1 小于 5，于是亲和度 1 的 A–C 被当成“更好”的一对。

结果是：同一张图，原网页第一步合并 A–C，最终 ACDE | B，cut 9；正确结果是 ABC | DE，cut 3。四个配置（K=2、K=3、容量 2、容量 3）原网页为 9/16/12/16，正确值为 3/8/8/3。原作的 Python 参考实现是正确的——问题只在网页 JS。

本课程引擎用逐字段比较的 compareKeys()，并专门加了 10 与 2、2.5 与 2 的回归测试，防止只对这张五节点图“碰巧正确”。

§ 4逐步推演：AB → ABC → DE

在 G01 上取 K = 2、不限容量。开始时 5 个单点簇，cut = 全部边权 = 18。

步骤当前的簇候选（亲和度）选中cut
0A, B, C, D, E——18
1A, B, C, D, EA–B 5，D–E 5，B–C 4，C–D 2，A–C 1，C–E 1A–B（平票 A < D）18 − 5 = 13
2AB, C, D, EAB–C 1+4=5，D–E 5，C–D 2，C–E 1AB–C（平票 [A,B] < [D]）13 − 5 = 8
3ABC, D, ED–E 5，ABC–D 2，ABC–E 1D–E8 − 5 = 3

第 2 步是关键：A 和 B 收缩成一个超节点后，A–C（1）和 B–C（4）是两条连到 C 的平行边，合起来 AB–C = 5。原作者特别画出了这一步，本课程的影片和实验都保留了它。

簇数降到 2，停止。结果 ABC | DE，剩下的 cut 是 C–D（2）和 C–E（1），共 3。

§ 5容量预览与停止状态

如果每个簇最多只能放 C 个单位大小（这里每个节点大小 1）：

  • 容量 3：AB+C 的大小 3 ≤ 3，合法，轨迹与上面相同，得 ABC | DE。
  • 容量 2：第 2 步的 AB+C 大小 3 > 2，被阻止；下一个合法候选是 D–E，合并。此时剩下 AB、C、DE：AB+C 是 3、C+DE 也是 3，都超容量，没有合法的正亲和度对——停止。

容量 2 的结果是 AB | C | DE，3 簇，cut 8，没有达到 K = 2。这不是程序出错，而是规则要求：没有合法合并就停下，并如实报告。这件事在 Module 04 会成为主角：区分“根本不可能”和“贪心走进了死胡同”。

三个状态要分开报告

合法（capacity compliant）：每个簇都没超容量——容量 2 的结果是合法的。达到目标（target reached）：簇数 ≤ K——容量 2 的结果没有达到。停止原因（stop reason）：target-reached、capacity-blocked（有正亲和度对但都超容量）或 no-positive-affinity（图不连通，剩下的簇之间没有边）。

§ 6逐行读懂伪代码

  1. clusters ← 每个节点一个单点簇
  2. while |clusters| > K:
  3. cands ← 所有亲和度 > 0 的簇对 (P, Q)
  4. legal ← cands 中 size(P) + size(Q) ≤ C 的
  5. if legal 为空: stop（如实报告未达到 K）
  6. (P, Q) ← legal 中选择键 (−亲和度, P, Q) 最小的
  7. 用 P ∪ Q 替换 P 和 Q
  8. return clusters, cut, 是否达到 K, 停止原因

点击任一行看解释；在实验中单步时，当前执行的行会自动高亮。

和 Python 的对应：第 6 行的选择键 → selection_key(c)；第 2–8 行 → greedy_pair_merge(...) 的主循环。

§ 7贪心的局限与工程含义

  • 不回撤：一旦合并就不再拆开。G01 上贪心恰好得到最小 cut 3，但这只是这张图的性质。Module 04 有一个反例：贪心得到 cut 18，而合法的最优分组只有 11。
  • 依赖评分：本模块用“簇间边权和”。换成 Module 02 的共同邻居等评分，合并顺序和结果都可能改变。
  • 复杂度：朴素实现每一步都要检查所有簇对。真实工具通常用优先队列，并只更新受合并影响的那几对。
  • 工程含义：在芯片设计中，这类自底向上的合并常用来把大量单元先粗化成较少的簇，再交给划分或布局工具；合并时通常还要限制簇的面积——这就是下一模块的容量约束。

08 / 常见错误与局限

容易错在哪里

每条都给错误结果、错因、反例和修正；反例的数值都由测试复算。

把候选数组当字符串比较

错误结果
原网页第一步合并了 A–C（亲和度 1），最终 ACDE | B，cut 9。
错因
JavaScript 的 cand < best 会把数组转成字符串再比较："-1,A,C" 排在 "-5,A,B" 前面，因为字符 1 小于 5。数值优先的规则被字符顺序取代。
反例 / 证据
同一张图、同一规则，正确比较得 ABC | DE，cut 3；四个配置原网页为 9/16/12/16，正确值为 3/8/8/3（本课程测试复现了两者）。
修正
逐字段比较：数字按数值，名字按字典序。本课程引擎用 compareKeys()，并对 10 与 2、2.5 与 2 做回归测试。

为了凑够 K 强行合并

错误结果
容量 2 时把 C 硬塞进 AB 或 DE，报告“得到 2 簇”。
错因
停止条件是“达到 K 或没有合法的正亲和度对”。没有合法对时就停，如实报告。
反例 / 证据
容量 2 时 AB+C 的大小是 3 > 2，C+DE 同样超容量；正确结果是 AB | C | DE，3 簇，cut 8，targetReached = false。
修正
结果里分开报告：实际簇数、是否满足容量、是否达到 K、停止原因。

忘记收缩后平行边相加

错误结果
合并 A、B 之后认为 AB–C 的亲和度只有 4（只看 B–C）。
错因
簇间亲和度是两簇之间所有边权之和：A–C 和 B–C 都连到 C。
反例 / 证据
AB–C = 1 + 4 = 5，和 D–E 并列；如果算成 4，第二步就会先合并 D–E。
修正
每一步按“簇对”重新累加跨簇边。

以为贪心总能找到最好的分组

错误结果
看到 G01 得到 cut 3，就认为贪心合并一般是最优的。
错因
贪心每一步只看当前最大的一对，合并后不能撤回；早期的选择会限制后面的可能。
反例 / 证据
Module 04 的 suboptimal 图：贪心得 cut 18，合法的最优分组 cut 11。
修正
把“这个例子得到 3”和“算法总是最优”分开说；需要保证时用穷举或其他方法对照。

适用范围与局限

  • 贪心不回撤：早期合并错了，后面无法纠正（Module 04 给出反例）。
  • 结果依赖评分与平票规则；换评分（Module 02）结果可能完全不同。
  • 朴素实现每步检查所有簇对；大规模电路通常配合优先队列与局部更新。
  • 容量在本模块只作预览，按节点大小之和计算；面积不同的单元要在 Module 04 里认真对待。
  • 本课程小图是教学用虚构数值。
